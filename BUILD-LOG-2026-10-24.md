# Build log — 2026-10-24

## Meeting Notes: persisted transcript + AI summary + `/notes/:id` (backlog item #3)

Closes the gap flagged in `BUILD-LOG-2026-10-23.md`'s "Remaining backlog" #3. The
live caption/Whisper transcript (`app/src/server.js` `caption` socket event +
`getWhisperTranscription`) only ever lived inside each peer's own browser tab,
carried peer-to-peer over the WebRTC DataChannel — the server never saw it, and it
was gone the moment every tab closed. There was already a client-only "Save
messages" button that downloads the transcript as a local `.txt`/JSON file
(`downloadCaptions()`), but nothing shareable and nothing summarized.

Built end to end, with real server logic and a real live call to the already-wired
OpenAI-compatible relay (not a stub) — verified by running the actual dev server and
exercising every new route with curl, not by adding automated tests.

- `app/src/meetingNotes.js` (new): on-disk JSON store, same pattern as
  `roomLink.js`/`roomClaims.js` — no database in this fork. Each record: id,
  `manageToken` (random 24-byte hex, compared with `crypto.timingSafeEqual` over a
  sha256 digest so length never leaks), roomId, createdAt, the normalized/capped
  transcript array, AI `summary` + `actionItems` + `summaryStatus`. Self-prunes
  (age + record-count caps) on every write — no new background timer.
- `app/src/server.js`:
  - `POST /api/v1/notes` — validates roomId, saves the transcript via
    `MeetingNotes.createNote`, then best-effort calls the same `chatGPT` client
    already instantiated for VCPeer Coworker (free `ai-relay-worker` by default) to
    generate `{summary, actionItems}` as JSON. The raw transcript is saved and
    servable regardless of whether the summary call succeeds — `summaryStatus` is
    one of `ready`/`failed`/`unavailable`. Returns `{ id, url, manageUrl,
    summaryStatus }`.
  - `GET /api/v1/notes/:id` — public read (never returns `manageToken`).
  - `DELETE /api/v1/notes/manage/:manageToken` — token-gated delete.
  - `GET /notes/:id` — serves the new static viewer page.
  - 3 new limiters in `app/src/middleware/rateLimiter.js`
    (`notesCreateLimiter`/`notesViewLimiter`/`notesDeleteLimiter`).
  - New `config.meetingNotes` section in `config.template.js` (+ local `config.js`,
    gitignored): size/retention caps, `MEETING_NOTES_DATA_DIR` env override
    following the same `*_DATA_DIR` convention as the other JSON stores.
- `public/views/notes.html` + `public/js/notes.js` + `public/css/notes.css` (new):
  dependency-free client-rendered viewer, same pattern as
  `public/js/clips/watch.js`/`watch.css` — loading/error/loaded states, copy-link
  button, summary + action-items sections (hidden if not ready), full transcript,
  and a delete button that only renders when `?manageToken=` is present in the URL
  (never discoverable from the plain share link).
- `public/views/client.html` + `public/js/client.js`: new "Share meeting notes"
  button in the caption panel's dropdown menu (next to the existing "Save
  messages"/"Clean messages" actions), wired to a new `shareMeetingNotes()` that
  POSTs the in-memory `transcripts` array + `roomId`, then shows the resulting
  shareable link in a Swal with a "Copy link" action (same Swal/`axios` pattern as
  the existing `maybeOfferRoomLink()`).
- `.gitignore` / `deploy/README.md`: `app/data/meeting-notes.json` added to the
  same never-commit / never-overwrite-on-redeploy list as `room-links.json`/
  `room-claims.json`/`notify.json`/`launchboard.json`.

## Round 2: same-origin `/schedule` create form + `/schedule/:id` + `.ics` export (backlog #6)

Before this round, the only "scheduling" flow in the product was the in-call
"Send email invitation" button (`public/js/client.js` `shareRoomByEmail`) — it
opens the visitor's own `mailto:` client with the chosen date/time typed into the
body as plain text. Nothing persists server-side, there's no page to revisit, and
no recipient ever gets an actual calendar file to import. Built the real thing:
a same-origin scheduling page with a server-persisted record and a
standards-compliant `.ics` file any calendar app can import.

- `app/src/schedule.js` (new): on-disk JSON store, same convention as
  `roomLink.js`/`roomClaims.js`/`meetingNotes.js`. Each record: `id`,
  `manageToken` (random 24-byte hex, compared via `crypto.timingSafeEqual` over a
  sha256 digest), `roomId` (user-chosen via `Validate.isValidRoomName`, or
  auto-generated + collision-checked against existing records when left blank),
  `title`, `description`, `organizerName`, `startTime` (UTC ms), `durationMinutes`,
  `createdAt`. Validates the meeting time is in the future (small clock-drift
  grace window) and not absurdly far out, and duration is within a sane 5–480
  minute range. Self-prunes by "meeting end + retention window" rather than
  `createdAt`, so a scheduled meeting's page/`.ics` link both keep working for a
  real look-back period after it actually happens, not just after it was booked.
  Also exports `buildIcs()`: a hand-rolled RFC 5545 `VEVENT` builder (UID,
  DTSTAMP/DTSTART/DTEND in UTC `Z` form, SUMMARY/DESCRIPTION/URL/LOCATION, proper
  TEXT-value escaping, and 75-octet line folding) — no new dependency.
- `app/src/server.js`:
  - `POST /api/v1/schedule` — create; returns `{ id, url, manageUrl, roomUrl, icsUrl }`.
  - `GET /api/v1/schedule/:id` — public read (never returns `manageToken`), adds
    the computed `roomUrl`.
  - `GET /api/v1/schedule/:id/ics` — serves the `.ics` file with
    `Content-Type: text/calendar` + `Content-Disposition: attachment`.
  - `DELETE /api/v1/schedule/manage/:manageToken` — cancel (token-gated, same
    `timingSafeEqual` pattern as Meeting Notes/Room Claims).
  - `GET /schedule` and `GET /schedule/:id` both serve the one static page below.
  - 4 new limiters in `app/src/middleware/rateLimiter.js`
    (`scheduleCreateLimiter`/`scheduleViewLimiter`/`scheduleIcsLimiter`/`scheduleCancelLimiter`).
- `app/src/config.template.js` (+ local `config.js`, gitignored): new
  `config.schedule` section — data dir, record cap, post-meeting retention
  window, field-length caps, duration bounds, max-future-date bound.
- `public/views/schedule.html` + `public/js/schedule.js` + `public/css/schedule.css`
  (new): one dependency-free page that does both jobs from a single script,
  same client-rendered pattern as `myRooms.js`/`notes.js`. No id in the URL →
  renders the create form (title/date-time/duration/optional room
  name/organizer/notes) and, on submit, swaps in a result card with Join /
  "Add to calendar" (direct `.ics` download) / "Google Calendar" (prefilled
  `calendar.google.com/render` link, computed client-side from the same
  start/duration) / copy-link, then rewrites the address bar to
  `/schedule/:id?manageToken=…` via `history.replaceState` so reloading or
  bookmarking the result keeps working. An id in the URL → fetches
  `GET /api/v1/schedule/:id` and renders the same result card; the Cancel button
  only ever appears when `?manageToken=` is present, never discoverable from the
  plain share link.
- `public/views/client.html` + `public/js/client.js`: new "Schedule a meeting"
  button next to the existing "Send email invitation" one in the room-security
  tab, opening `/schedule?roomId=<currentRoom>` in a new tab so the invite points
  back at the room the organizer is already in.
- `public/views/landing.html` nav + `public/sitemap.xml`: added `/schedule` so
  it's discoverable and indexable (distinct from the existing
  `/free-scheduling-link` SEO page, which correctly describes the separate
  Cal.com-backed `book.vcpeer.com` availability-booking flow — this one is a
  simpler single-meeting "pick a time, get a link + `.ics`" tool, not a
  duplicate claim).
- `.gitignore` / `deploy/README.md`: `app/data/schedule.json` added to the same
  never-commit / never-overwrite-on-redeploy list as the other `*_DATA_DIR` files
  (now 8 excludes in the rsync commands, up from 7).
