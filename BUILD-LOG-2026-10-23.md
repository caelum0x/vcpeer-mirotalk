### 1. Host-controlled guest lobby (knock-to-join)

Closes the real security gap: before this, anyone who guessed/brute-forced a room name
could join a live call outright — there was no per-guest admission control, only the
"host hasn't started the room yet" wait page.

- `app/src/server.js`:
  - New in-memory `lobbyPending` queue (room -> socket.id -> knock entry), `'lobby'`
    added to `roomMetaKeys`.
  - Split socket `'join'`'s completion logic out of the inline handler into a reusable
    module-level `completeJoin(channel, peerSocket, config, isPresenter)` +
    `addPeerToForSocket(channel, targetSocket)`, so the exact same WebRTC-wiring /
    serverInfo / first-peer-alert / webhook code path can run either immediately or
    later, once a host admits a knocking guest.
  - New socket events: guest emits the existing `'join'`; if the room's `lobby` flag is
    on and the peer isn't the presenter, the server parks them in `lobbyPending`,
    emits `'knockPending'` back to the guest, and pushes `'lobbyUpdate'` (the full
    pending list) to every presenter in the room. Host decides via `'admitGuest'` /
    `'rejectGuest'` (authorized the same way `roomAction` already is — server-controlled
    `socket.id` matched against the stored presenter entry, never a client-supplied
    peer_id). Guest gets `'knockAdmitted'` or `'knockRejected'`.
  - `roomAction` gets `'lobbyOn'` / `'lobbyOff'` cases (same shape as the existing
    `lock`/`joinLock` cases). Turning the lobby off admits everyone still waiting
    instead of silently dropping their request.
  - Disconnect cleanup for a guest who closes the tab while still knocking; lobby queue
    is cleared when a room fully empties out.
- `public/js/client.js`: `lobbyOnBtn`/`lobbyOffBtn` toggle wiring + `handleRoomStatus`
  cases; a dynamically-built floating "Waiting to join" panel (admit = check icon,
  decline = x icon — no text-labelled "Enter" button, glyphs only) rendered from
  `lobbyUpdate`; guest-side `knockPending`/`knockAdmitted`/`knockRejected` handlers using
  the existing Swal pattern (non-dismissible "waiting for host" loading state, then
  either closes or shows a "not admitted" message and redirects to `/newcall`).
- `public/views/client.html` + `public/css/client.css`: the two toggle buttons in the
  room-security tab, plus the floating panel's CSS (built with the existing `--ds-*`
  design tokens).
- Verified live: a socket.io-client script drove host-join → `lobbyOn` →
  guest-knock → `lobbyUpdate` → `admitGuest` → guest `addPeer`/`serverInfo` — full
  sequence confirmed in server logs with zero errors.

### 4. Durable named rooms with a reusable passcode

`roomPassword.js` only ever supported an ad-hoc, in-memory, per-call password — nothing
survived a restart or an empty room. Agencies/recruiters who reuse the same link every
week had no way to "claim" a room name with a fixed passcode.

- `app/src/roomClaims.js` (new): JSON-file store keyed by room name. Passcodes are
  **never stored in plaintext** — random per-claim salt + `crypto.scryptSync`-derived
  hash (Node's built-in crypto, no new dependency), compared with
  `crypto.timingSafeEqual`. Re-claiming/updating an already-claimed name requires
  proving the *current* passcode first (so a stranger can't steal/relock someone
  else's claim). Releasing also requires the current passcode.
- `app/src/server.js`:
  - `POST /api/v1/rooms/claim`, `POST /api/v1/rooms/claim/release`,
    `GET /api/v1/rooms/claim/status` (new `roomClaimLimiter` / `roomClaimStatusLimiter`).
  - Enforced in the socket `'join'` handler: a claimed room's passcode is checked for
    **every** join attempt, including the very first joiner of a brand-new session
    (unlike the ephemeral `RoomPassword` lock, which only applies once someone has
    already locked an active room) — reuses the same IP+room brute-force throttle as
    the ephemeral lock.
  - Fixed the pre-join `roomAction` `'checkPassword'` path, which previously
    hard-required `peers[room_id]` to already exist (`if (!peers[room_id]) return;`)
    and would have thrown on `peers[room_id]['lock']` for a claimed-but-never-opened
    room. It's now claim-aware and works even with zero live peers, so the existing
    client-side "enter the room password" flow (`handleUnlockTheRoom` → `checkPassword`
    → `joinToChannel()`) works for claimed rooms with **no new client UI needed for
    passcode entry at join time**.
- `public/views/customizeRoom.html` + `public/js/customizeRoom.js`: new "Claim this
  room name" step on `/customizeRoom` — debounced claim-status check as the room name
  field changes, passcode/current-passcode/owner-email fields, Claim + Release buttons,
  all calling the new API routes directly with `fetch` (matching this file's existing
  vanilla-JS style, no axios needed here).
- `.gitignore` / `deploy/README.md`: `app/data/room-claims.json` added to the same
  never-commit / never-overwrite lists.
- Verified live end to end with a socket.io-client script: claim → join without
  passcode (`roomIsLocked`) → `checkPassword` with wrong passcode (`KO`) →
  `checkPassword` with correct passcode (`OK`) → full join with correct passcode
  (succeeds, becomes presenter) → release (requires correct passcode, wrong one
  rejected).
